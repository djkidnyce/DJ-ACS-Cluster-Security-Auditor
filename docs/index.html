DJ's ACS Auditor

Audit Kubernetes and OpenShift manifests against Red Hat Advanced Cluster Security policy logic, score and rank every finding, and fix it in YAML with a preview and an explicit confirmation before anything changes.

View on GitHub Releases
No command is ever run to remediate a finding. Fixes are text edits to YAML, handed back to you as files. Nothing touches a cluster, nothing calls oc, kubectl or roxctl, and nothing is applied behind your back. The one subprocess in the whole tool is git status, used to refuse an in place write on a dirty tree.

What it is

One HTML file you open from disk. No install, no server, no package manager, no runtime. It has two tabs: Audit reads, scores and reports; Remediate edits the YAML you loaded, with a diff and a confirmation for every change and undo all the way back.

There is also a command line runner for pipelines, and shell scripts that pull findings out of ACS. Those need curl and jq; the CLI needs Node. The audit itself needs neither.

It exists to close one gap

ACS tells you a running workload is in violation. It does not hand you a corrected manifest, and it does not tell you what your posture becomes once the fix lands. This does both, against the manifest in your repository, which is where the fix actually has to be made.

Report, manual, or auto. You choose, every time.

ModeProducesModifies anything
reportThe analysis. Report, JSON, SARIF. Nothing that could be applied.No
manualPatches and written guidance for a human to reviewNo
autoApplies the safe fixes and writes corrected YAMLYes, with preview and confirmation

report is the default on every surface. The safe state is the one you get by doing nothing, not the one you get by remembering a flag. The mode is never inferred: asking for patches while in report mode is refused with an explanation rather than quietly upgraded.

Why that is a security control and not a convenience. A remediation tool that can write before the operator has chosen to write is a new risk, not a mitigation. The failure is not the tool doing something malicious. It is someone at the end of a long incident clicking the obvious button, producing a change to a production manifest they did not intend, and defending it in review with a plausible looking diff attached.

What it covers, stated as a number

Twenty policies. ACS ships roughly seventy defaults and most teams add their own, so a clean score here means clean against twenty checks, not compliant with the ACS default set. It should never be quoted as the latter.

Build stage rules, runtime behaviour policies and image CVE policies cannot be judged from a manifest at all. Violations this tool does not model arrive through your ACS export and are shown as unmatched rather than dropped, because a scanner that discards what it does not understand is indistinguishable from one that found nothing.

Automatic does not mean safe for your workload

An automatic fix means the edit to the YAML is unambiguous. It says nothing about whether your application survives it. Four of them can stop a workload that relied on what gets removed:

  • readOnlyRootFilesystem on anything that writes to disk
  • dropping all capabilities from an image that needs one
  • runAsNonRoot against an image with no numeric non-root user
  • unmounting the service account token from a pod that calls the Kubernetes API

Each carries a note naming the failure and the remedy, in the confirmation dialog, the change log, the patch header, the CLI output and the report. Test them somewhere you do not care about first.

Getting findings out of ACS

The page never contacts anything. A page opened from a file has a null origin and no API will accept it, so an in browser connector could only ever have asked for a live token in exchange for a request the browser blocks. The scripts do it instead, from a shell where the cluster is reachable and the token stays out of ps and shell history.

export ROX_ENDPOINT=https://central-stackrox.apps.example.com
export ROX_API_TOKEN=<token>
./scripts/acs_preflight.sh
./scripts/acs_pull_all.sh -o findings

Central's certificate is self signed by default, so the first run will fail verification. That is expected. The script resolves it in order of trustworthiness: a CA you supplied, then the central-tls secret read through your authenticated oc session, and failing both it prints the certificate's fingerprint and two commands that work. --insecure is never offered as a shortcut.

Each run ends by writing and printing findings.md, a summary you can read or hand over. That part needs only jq.

Two ACS data planes, and why an empty alert list proves nothing

An image CVE is not a policy violation. It only produces an alert if somebody wrote a policy that fires on it, and most teams have not. A cluster full of critical, actively exploited CVEs can return an empty /v1/alerts list. Empty is not clean, it means you asked the wrong endpoint.

PlaneEndpointThe catch
Policy violationsGET /v1/alerts Returns a slim projection with no violation text at all, and the namespace under commonEntityInfo. Only /v1/alerts/{id} has the detail. This tool lists, then hydrates.
Image vulnerabilitiesGET /v1/export/vuln-mgmt/workloads Streams NDJSON, so res.json() fails on it. The token needs read on Image and Deployment, which is the usual reason a CVE pull comes back empty while alerts keep working.

Running where Node cannot be installed

Normal on a hardened host in a controlled enclave, and a supported path rather than a limitation. The page gives you the posture, the violations, the fix routes, the drafted YAML and the full report, and needs only a browser. The pull scripts need curl and jq. scripts/acs_summary.sh gives you a markdown summary from the shell using jq alone. Only the headless CLI and the test suite need Node.

Limits

Static analysis of manifest text, plus whatever ACS hands you. It does no scanning of its own: if ACS has not scanned an image this tool has nothing to say about it, and says so rather than showing a reassuring zero. It does not replace ACS, admission control such as Pod Security Admission or Kyverno, or runtime enforcement.

Policy names, severities and remediation text are modelled on the ACS defaults with the structure verified against the upstream StackRox definitions. Check them against your own ACS version; defaults shift between releases and most teams tune them. STIG references are mapping aids and must be verified against the current DISA release before being cited in an accreditation package.

Written and reviewed by one person. This has not had an independent security review. It is offered as a working tool, not an audited one, and the source is small enough to read before you trust it.
