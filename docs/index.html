What it does

Red Hat ACS tells you a running workload is in violation. It does not hand you a corrected manifest, and it does not tell you what your posture becomes once the fix lands. This closes that gap, against the manifest in your repository, which is where the fix has to be made.

Audit

Twenty policies mirroring the ACS defaults, with CIS, NIST 800-53, Pod Security Standards and DISA STIG citations on every finding.

Score

A weighted posture score whose denominator comes from what was scanned, never from what was found, so the projection survives a rescan.

Fix

Patched YAML, strategic merge patches for Helm and Kustomize, a change log, and a CVE rebuild worklist grouped by image.

Report, manual, or auto. You choose, every time.

ModeProducesModifies anything
report The analysis. Report, JSON, SARIF. Nothing that could be applied.No
manual Patches and guidance for a human to review and apply.No
auto Applies the safe fixes, with a preview and confirmation for each.Yes

report is the default on every surface. The safe state is what you get by doing nothing, not what you get by remembering a flag. The mode is never inferred from another option, an unknown mode is an error rather than a quiet fall back to something permissive, and the mode is recorded in every artifact so a reviewer holding a patch never has to ask which path produced it.

Why that is a security control and not a convenience A remediation tool that can write before the operator has chosen to write is a new risk, not a mitigation. The failure is not the tool doing something malicious. It is somebody at the end of a long incident clicking the obvious button, producing a change to a production manifest they did not intend, and then defending it in review because a plausible looking diff is attached.

The guarantee

No command is ever run to remediate a finding. Every fix is a text edit made to YAML and handed back to you as a file. The tool does not call oc, kubectl, roxctl, helm, or a shell. It does not write to a cluster. Live connect is read only GET, and only when you ask.

  • No exec, eval or Function constructor in any shipped file, asserted on every test run.
  • No API token is written to browser storage, and every token field is cleared in a finally block so a failed call does not leave a credential in the DOM.
  • URLs arriving from an ACS export are scheme allowlisted before they reach an href, so javascript: and data: cannot execute.
  • Dependencies are vendored with published SHA-256 values. No package manager, no network.

Two ACS data planes, and why an empty alert list proves nothing

An image CVE is not a policy violation. It only produces an alert if somebody wrote a policy that fires on it, and most teams have not. A cluster full of critical, actively exploited CVEs can return an empty /v1/alerts list. Empty is not clean, it means you asked the wrong endpoint.

PlaneEndpointThe catch
Policy violationsGET /v1/alerts Returns the slim ListAlert with no violations array, and namespace under commonEntityInfo. Only /v1/alerts/{id} has the detail. This tool lists, then hydrates.
Image vulnerabilitiesGET /v1/export/vuln-mgmt/workloads Streams NDJSON, so res.json() fails on it. Needs read on Image and Deployment, not just Alert, which is the usual reason a CVE pull comes back empty while alerts keep working.

Since ACS 4.6 the console Violations page also defaults to user workloads and hides platform components behind a selector, so a default API pull can differ from what is on screen. This tool asks for both.

Quick start

In a browser, nothing installed

git clone https://github.com/djkidnyce/DJ_ACS_cluster_security_auditor.git
cd DJ_ACS_cluster_security_auditor
open dj_acs_auditor.html        # or double click it

From a terminal or a pipeline

# report only, the default
node acs_cli.js --path ./manifests --report --json

# manual: patches for a human to apply, nothing modified
node acs_cli.js --path ./manifests --mode manual --patches --out ./proposed

# auto: apply the safe fixes to a copy
node acs_cli.js --path ./manifests --mode auto --patches --out ./remediated

# CI gate, SARIF into the security tab
node acs_cli.js --path ./manifests --sarif --fail-on high

Pull everything ACS knows

export ROX_ENDPOINT=https://central-stackrox.apps.example.com
export ROX_API_TOKEN=<token>
./scripts/acs_pull_all.sh -o findings

Run ./scripts/acs_preflight.sh first if anything is not working. It tells you which server you are actually pointed at, whether the token authenticates, and exactly which resources it can read.

Limits, stated plainly

  • This is static analysis of manifest text plus whatever ACS hands you. It does no vulnerability scanning of its own.
  • It does not replace ACS, admission control such as Pod Security Admission or Kyverno, or runtime enforcement. It fixes the manifest before any of those have to reject it.
  • Policy names, severities and remediation text are modelled on the ACS defaults, verified against the upstream StackRox definitions. Confirm them against your own ACS version.
  • STIG references are mapping aids. Verify against the current DISA release before citing them in an accreditation package.
  • There is no auto fix for a CVE, deliberately. ACS reports fixed package versions, not fixed image tags, and deriving one from the other means guessing.
