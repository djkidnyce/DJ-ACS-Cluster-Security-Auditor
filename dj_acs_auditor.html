Policy violations Vulnerabilities (CVEs) OpenShift API

Leave detail fetching on. GET /v1/alerts returns the slim ListAlert, which carries a policy name and severity but no violation text at all. Only GET /v1/alerts/{id} returns the full alert with violations[]. Listing alone is why the results can look empty. Detail is fetched one alert at a time, capped at 200, so this page does not hammer Central.

The console does not show you both by default. Since ACS 4.6 the Violations page has a user workloads, platform, or both selector, and it opens on user workloads. Anything you can see there under the platform view is missing from a default API pull. This defaults to both, because hiding half the estate behind a filter you did not set is not an audit. On ACS older than 4.6 the field does not exist and the query falls back automatically.

Create a token in ACS under Platform Configuration, Integrations, Authentication Tokens, API Token. Give it a role with read access to alerts, nothing more.

CVEs are not policy violations, and they are not in /v1/alerts. An image vulnerability only produces an alert if somebody wrote a policy that fires on it, so a cluster riddled with critical CVEs can return an empty alert list. This tab uses the separate vulnerability export, /v1/export/vuln-mgmt/workloads, which is where CVE data actually lives.

The token needs read access to Image and Deployment. A token scoped only to Alert returns 403 here while the violations tab keeps working, which is a confusing failure worth knowing about in advance. The export streams NDJSON and a large cluster takes a while.

Already have an export on disk from curl or roxctl? Drop the .ndjson or .json file onto the drop zone above with your manifests. No connection needed.

Pulls Deployments, DaemonSets, StatefulSets and CronJobs, strips the server side fields, and audits what is actually running. Comparing that against your git manifests is often where the interesting gap shows up.

How your token is handled. It stays in a variable in this tab for the duration of the request. It is never written to storage, never logged, never included in any export, and it is gone when you close the tab. Nothing is sent anywhere except the URL you typed. Use a short lived, least privileged, read only token anyway.

Left bar is where you are now, right bar is where you land once every automatically fixable finding is applied. Both are measured against the same total, so the two numbers are directly comparable. Apply the fixes on the remediation page.

Cross check against your ACS export

Report only produces the written account of what could be fixed and by which route, and no patch files at all. Manual adds the patches. There is no auto option here on purpose: these patches are built from a violation rather than from a manifest this tool has seen, so a human has to look at them before they go anywhere near a cluster.

Image vulnerabilities

Deliberately kept out of the posture score above. The configuration posture has a fixed denominator derived from what was scanned, which is what makes the before and after numbers comparable. CVE counts change every time a vulnerability feed updates, with nothing in your manifests changing at all. Folding them together would produce a score that moves for reasons you did not cause and cannot act on, so these are reported separately.

Severity Priority CVE Component Fixed in Image Why it ranks here

Priority runs 0 to 15, not 0 to 10, because clamping to 10 would make every critical tie at the top and destroy the ordering exactly where it matters. It is CVSS plus named, bounded adjustments, all listed in the last column. It is not a CVSS score and should not be quoted as one.
